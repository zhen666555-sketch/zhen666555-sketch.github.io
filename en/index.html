LongqingxiaScenic-area ticketing platform

A WeChat mini program, operations dashboard and Java transaction service for ticket selection, payment confirmation, issuance, orders and refunds.

WeChat Mini ProgramsJava 21Spring Boot 3.5MyBatisMySQLFlyway
Expand implementation details

My roleFull-stack developer intern

Business context

Visitors buy tickets, manage contact details and look up tickets in the mini program. Staff manage attractions, products, orders and refunds in the dashboard. The backend integrates with WeChat and a third-party ticketing provider, connecting user actions to external transaction states.

  1. Select tickets and contact
  2. Create order snapshot
  3. Confirm payment on server
  4. Issue and look up tickets

Architecture

The visitor mini program and embedded admin dashboard call REST APIs. Java 21 and Spring Boot 3.5 handle transactions, MyBatis and MySQL store business data, and Flyway manages schema migrations. Nginx and Tencent Cloud CVM support deployment.

Key implementation details

  • Separated transaction inputs from external side effects. Idempotency keys and snapshots of amounts, products and contact details lock in the order inputs. Tickets are issued after server-side payment confirmation rather than on a client callback alone.
  • Used a persistent outbox, task retries and manual reconciliation to handle external failures or unknown outcomes without blindly repeating issuance or refunds.
  • Classified orders before pagination to keep lists, details and counts consistent. Shared tickets use the provider's actual ticket codes and distinguish used, refunded, remaining and currently available quantities.
  • Coalesced concurrent session refreshes on HTTP 401 and guarded against stale session overwrites. Streamlined loading with home-page snapshots, detail summaries, image variants, versioned URLs and ETag / 304 responses.

Scope and limitationsPayment, ticket issuance and refunds have implementation and backend delivery records. Live settlement, provider retries, gate validation and complete device flows require separate acceptance checks.

An event platform for participants, organizers and staff, covering event review, registration, fee snapshots, insurance records and check-in validation.

My roleFull-stack developer intern

Business context

Participants browse and register for events. Approved organizers publish events, and staff handle event, personnel and insurance tasks. The mini program, dashboard and backend share the same business records so rule changes can be reconciled with existing registrations.

  1. Organizer application
  2. Event review
  3. Registration and fee snapshot
  4. Insurance records and check-in

Architecture

The WeChat mini program and same-origin HTML, CSS and JavaScript dashboard call a Node.js HTTP API. MySQL handles relational data and transactions, COS stores private images, and GitHub Actions and CVM support checks and delivery.

Key implementation details

  • Linked publishing eligibility, event review, registration and QR check-in. Server-side checks cover ownership, cancellations, event and policy dates, and duplicate check-ins while preserving the first check-in time.
  • Stored money in integer cents and captured base and insurance fees at registration. Version checks prevent conflicting settings updates, and new rules do not rewrite existing events or registrations.
  • Migrated JSON snapshots to core relational tables. Foreign keys, a uniqueness constraint for active registrations, transactions and revision-checked updates protect consistency. Writes stop on failure or conflict.
  • Integrated WeChat sessions and logout revocation. The admin dashboard uses role permissions, scrypt, CSRF protection and auditing. Sensitive fields are encrypted, private avatars use short-lived signed URLs, and backups and rollback are available.

Scope and limitationsFee calculations and policy records are separate. They do not indicate that live payments, fund splitting or automated insurance issuance are enabled. Funds, underwriting and device workflows are checked separately.

Bike-share and metro transfer analysisGeospatial data and interpretable modelingPython / Flask / GeoPandas / NetworkXNov 2025 – Apr 2026+

My roleFull-stack development

Context and goals

Studied bike-share transfers to the Shenzhen metro by combining trips, physical stations and points of interest. Compared demand by station and hour and examined associations with spatial, temporal and network features.

Architecture

Flask Blueprints and a service layer handle computations and queries. Jinja, JavaScript, Chart.js and Leaflet render the UI. CSV stores analysis data, Joblib stores models and scalers, and JSON stores metrics and explanations.

  1. Station and POI features
  2. Station-by-hour samples
  3. Training and explanations
  4. Save and restore results

Key implementation details

  • Reused cleaned bike-share records and processed 236 physical stations and 1,364,135 POIs. Used a metric projection, exact 500-meter distance checks and interchange deduplication for features, then computed network metrics with NetworkX.
  • Compared an OLS baseline with XGBoost using hourly sine and cosine, peak-period, POI and centrality features. Split by physical station and fitted scaling inside GroupKFold to prevent overlap and preprocessing leakage.
  • The training endpoint returns metrics, SHAP and PDP data and stores the model, scaler and feature list. A latest-results endpoint restores results after refresh, and the PDP endpoint recomputes plots for the selected feature.
  • Applied log1p and expm1 to the XGBoost target. Evaluated in original transfer-count units and inverse-transformed individual PDP predictions before averaging. The UI distinguishes untrained models, missing results and unavailable AI configuration.
Python / FlaskGeoPandasNetworkXOLS / XGBoostSHAP / PDPChart.js / Leaflet

Scope and limitationsHeld-out stations test generalization to unseen stations, not forecasts for future dates. SHAP and PDP describe model associations, not causality or guaranteed accuracy. Existing records do not indicate a new training run.
