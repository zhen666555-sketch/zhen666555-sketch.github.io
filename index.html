龙庆峡文旅票务平台

面向游客与运营人员，连接原生小程序、运营后台和 Java 交易服务，处理选票、支付确认、出票、订单及退款。

微信原生小程序Java 21Spring Boot 3.5MyBatisMySQLFlyway
展开工程细节

参与范围全栈开发工程师（实习）

业务场景

游客需要在小程序中完成门票选购、联系人维护和票券查询；运营人员通过后台管理景区内容、商品、订单与退款。服务端统一对接微信与第三方票务，承接前端交互和外部交易状态。

  1. 选票与联系人
  2. 创建订单快照
  3. 服务端确认支付
  4. 出票与票券查询

系统组成

游客小程序与内嵌运营后台调用 REST API；Java 21 / Spring Boot 3.5 组织交易服务，MyBatis / MySQL 保存业务数据，Flyway 管理结构迁移，Nginx 与 CVM 承接服务交付。

关键实现

  • 交易输入与外部副作用分开处理：以幂等键及金额、商品、联系人快照固定订单输入，通过服务端支付确认驱动出票，避免将客户端返回直接视为出票成功。
  • 用持久化 outbox、任务重试与人工对账承接外部失败或结果未知场景，避免盲目重复出票、退款，并保留后续核对依据。
  • 订单先分类再分页，统一列表、详情与统计口径；按实际供应商票码展示多人共享票，区分已用、已退、剩余及当前可用数量。
  • 前端请求合并并发 401 续期并保护会话覆盖，结合首页快照、详情摘要、图片派生规格、版本化 URL 与 ETag / 304 梳理加载路径。

实现范围支付、出票与退款有实现及服务端交付记录；真实到账、供应商重推、闸机核销和完整真机链路需分别验收，不据此宣称全部交易路径已上线。

业务场景

  1. 主理人申请
  2. 活动审核
  3. 报名与费用快照
  4. 保险登记与核销

系统组成

微信原生小程序与同源 HTML / CSS / JavaScript 后台对接 Node.js 原生 HTTP API；MySQL 承接关系数据与事务，COS 保存私有图片，GitHub Actions 与 CVM 支持检查和版本交付。

关键实现

  • 将发布资格、活动审核、报名和扫码签到串联；服务端校验对象归属、取消状态、活动与保单时间及重复核销，保留首次签到时间。

场景与目标

面向深圳共享单车与地铁接驳，将单车出行、物理站点和 POI 组织到统一流程，观察站点与小时差异，并比较空间、时间和网络特征与接驳需求的关联。

系统组成

Flask Blueprint 与服务层承接计算和查询，Jinja / JavaScript、Chart.js 与 Leaflet 展示页面；CSV 保存分析数据，Joblib 保存模型与标准化器，JSON 保存指标和解释。

  1. 站点与 POI 特征
  2. 站点—小时样本
  3. 训练与解释
  4. 结果保存与恢复

关键实现

  • 复用既有单车清洗结果，处理 236 个物理站点和 1,364,135 条 POI，以米制投影、500 米精确距离及换乘站去重构建特征，再用 NetworkX 计算网络指标。
  • 以 OLS 为基线对比 XGBoost，加入小时 sin / cos、峰时、POI 和中心性；按物理站点隔离训练与测试，在 GroupKFold 内拟合标准化，防止同站小时样本与预处理泄漏。
  • 训练接口返回 metrics / shap / pdp，保存模型、标准化器和特征清单；最近结果接口支持刷新恢复，PDP 接口按所选特征重新计算，而非只替换图表标题。
  • XGBoost 目标使用 log1p / expm1；在原始接驳次数尺度评估，并让 PDP 逐样本还原后再求均值。页面对未训练、结果缺失和 AI 配置不可用分别反馈。
